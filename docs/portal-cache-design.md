# 本地缓存库与飞书双向同步（设计记录 · 2026-10-21）

## 1. 目标

改造前，网页的每次写入都直接同步调用飞书，写完再触发一轮同步，页面要等 2.5 秒后才刷新。
改成：**网页改动先实时写进本地库、马上生效，再由后台推到飞书**；飞书侧的改动走反方向，
合并回本地库。整件事分六步：

| 步骤 | 内容 | 状态 |
| --- | --- | --- |
| 1 | 冲突规则 | **已完成**（本文 §2，代码 `app/portal/cache_rules.py`） |
| 2 | 本地库结构（库版本 1 → 2）+ 迁移 + 飞书镜像 | **已完成**（本文 §3–§5） |
| 3 | 网页写入改走队列 + 后台推送线程 | **已完成**（本文 §6），2026-10-29 起默认 `PORTAL_WRITE_MODE=cache`（回滚设 `direct`） |
| 4 | 读接口看到本地改动（快照由「镜像 ⊕ 未落地操作」生成） | **已完成**（本文 §7） |
| 5 | 前端：写完立即刷新、显示同步状态 | **已完成**（本文 §8） |
| 6 | 按表逐步切换到 cache 并上线 | **进行中**：2026-10-21 已部署生产，第一批日程、事项、项目已切到 cache；采购、考勤待第一批跑稳后再切 |

## 2. 冲突规则（第 1 步，2026-10-21 与维护者确认）

所有规则都是纯函数，见 `app/portal/cache_rules.py`，测试见 `tests/test_cache_rules.py`。

### 2.1 修改：字段级三方合并

网页改了哪些列就只推哪些列。推送前取飞书当前值（remote），与编辑当时的基准（base）、
本地新值（local）逐列比较：

| 情况 | 处理 |
| --- | --- |
| remote 已经等于 local | 不用推 |
| remote 仍等于 base（飞书没动过这一列） | 推 local |
| 两边都改了且不一致 | **冲突，以飞书为准**（这一列不推），记一条冲突给组长看 |
| 飞书改了 A 列、网页改了 B 列 | 不算冲突：B 照推，A 保持飞书的值 |
| 飞书侧记录已删除 | 本地修改作废，记冲突（`remote_deleted`） |

### 2.2 删除

推送前只核对调用方指定的列（`watch_cols`，应传**门户可写的列**）。这些列在飞书侧有改动时
**不删**，以飞书为准并记冲突（`delete_blocked`）。飞书侧早已删除的视为完成。
公式列会随时间自己变化（剩余天数、周时长），所以不能拿它们来比较，否则所有删除都会被拦下。

### 2.3 考勤时长按增量记

签退时本地记一条考勤明细（签到、签退时间和时长）。推送时**取飞书当前累计值，再加本次时长**，
永远不整数覆盖。这样即使飞书上有人手改过时长，也不会被网页覆盖。

### 2.4 新建与临时 ID

新建记录先分配本地临时 ID（`loc_` 开头，飞书 record_id 都以 `rec` 开头，不会撞）。
推送成功后在 `id_map` 里对应上；排在后面、挂在临时 ID 上的操作会改挂到飞书 ID。
详情页链接用临时 ID 也要能打开（`local_alias()` / `resolve_id()`）。

### 2.5 值比较前先归一

同一列在读接口和写接口里的形状不同，比较前统一用 `canon()` 归一：

| 列类型 | 读回 | 写入 | 比较时只看 |
| --- | --- | --- | --- |
| 人员 | `[{id, name, email…}]` | `[{id}]` | id 集合 |
| 关联 | `[{record_ids, table_id, text…}]` | `["rec…"]` | record_id 集合 |
| 附件 | `[{name, url, file_token…}]` | `[{file_token}]` | file_token 集合 |
| 数字 | `"12.5"`（字符串） | `12.5` | 数值（保留 6 位小数） |
| 公式文本 / 富文本 | `[{text, type}]` | 字符串 | 拼接后的纯文本 |
| 多选 | 字符串数组 | 字符串数组 | 集合（顺序不算改动） |
| 空值 | 键不存在 | `null` / `""` / `false` / `[]` | 一律视为空 |

已知取舍：数字列和文本列分不出来，所以 `"1.0"` 和 `"1"` 这类纯数字文本会被视为相等。

## 3. 库结构（第 2 步，库版本 2）

新表和快照放在同一个库文件 `config/portal_snapshot.db`，所以现有备份脚本会自动把它们备份进去。
表结构定义在 `app/portal/migrations.py`，读写函数在 `app/portal/cache_store.py`。

| 表 | 作用 |
| --- | --- |
| `remote_records` | **飞书镜像**：每轮同步拉到的原始记录（键是飞书列名，值是读形状），附飞书最后修改时间与修改人。它是合并基准 |
| `outbox` | **待推送队列**：每条网页改动一行（新建 / 修改 / 删除），带要写的列、增量列、基准、幂等键 `client_token` |
| `id_map` | 本地临时 ID ↔ 飞书 record_id |
| `conflicts` | 冲突记录：哪条记录、哪一列、基准 / 本地 / 飞书三个值；组长确认后记 `acked_at` |
| `attendance_sessions` | 考勤明细：每次签到一行；同一人同一时刻最多一条未闭合（唯一索引保证） |

### 3.1 队列状态

```
pending（待推）──claim──▶ pushing（推送中）──▶ done（完成）
   ▲                         │                 failed（永久失败，等人处理）
   └──── 临时失败，退避 ──────┘                 conflict（整条因冲突放弃，飞书优先）
pending ──被后续操作取代──▶ cancelled
```

- **同一记录严格按顺序推**：前面还有 pending/pushing 的操作，后面的就取不出来；不同记录互不阻塞。
- **合并**：同一记录还没开始推的修改会合并成一条：同一列取最新值，基准保留最早那次的。
  已经尝试推过的操作不再合并。新建可能已经在飞书落了库，这时再改它的字段，改动会丢。
- **新建还没推出去就被删除**：新建和后续修改一起作废，飞书上什么都不发生。
- **服务异常退出**：停在 pushing 的操作由 `requeue_stuck()` 放回 pending。新建靠 `client_token`
  幂等，重推不会在飞书产生重复记录（飞书接口的幂等行为在第 3 步实测）。

### 3.2 基准取「本地视图」

编辑时的基准不是直接取镜像，而是**镜像叠加所有未落地操作**之后的样子（`apply_ops()`）。
否则自己正在推的改动会被当成飞书侧的改动，下一次编辑必然报假冲突
（`tests/test_cache_store.py::test_base_includes_in_flight_push`）。

### 3.3 镜像刷新

现有同步每轮都会把原始记录写进镜像（`sync._refresh_mirror`），内容没变就不写库。
列记录接口加了 `automatic_fields=true`，用来取回 `last_modified_time`；2026-10-21 已在正式库实测，
8 张表全部返回毫秒时间戳。两条保护：

- 镜像行的写入时间晚于本轮拉取开始时间（推送成功后写回的）→ 不覆盖、不删除；
- 镜像里的飞书修改时间比本轮拉到的更新 → 不回退。

**第 4 步起页面快照由镜像生成**：镜像刷新失败即整轮同步失败（保留上一版快照），并记 meta `remote_mirror_error`。

## 4. 迁移与回退

- 服务启动时**不会**自动迁移，版本闸门仍是故障关闭。旧库升级只走 `scripts/portal_migrate.py`：
  先用 sqlite3 backup API 备份并校验完整性，再在单个事务里建表、改版本号，最后再校验一次。
- 迁移只加新表，**可以在旧服务运行时执行**：旧进程已经过了版本闸门，会照常读写，重启后换新程序。
- `deploy.py` 在重启服务前自动执行迁移，备份放在 `/opt/portal-backups/<时间戳>/premigrate/`。
  迁移失败就中止部署、不重启，旧进程照常运行。
- 回退到旧程序：停服务 → 用 `premigrate/portal_snapshot.v1.db` 覆盖库文件并删掉同名 `-wal/-shm`
  → 换回旧代码 → 启动。第 3 步上线以后，回退会丢掉队列里还没推出去的改动，回退前要先确认队列为空。
- 2026-10-21 已在本机开发库的副本上实测：迁移成功，快照完好，随后对真实飞书跑一轮同步，镜像写入 41 行。

## 5. 第 2 步交付后的实际状态

- **线上行为不变**：网页写入仍然直写飞书；读接口仍读快照。除了镜像，新表都还没有数据。
- 新增的写库只有镜像刷新：每轮同步在内容有变时写一次，内容不变不写。
- 备份清单 `manifest.json` 的 `snapshot` 里多了 `outbox_open` / `conflicts_open`。恢复时会打印未推送条数。
  这些改动只存在本库里，所以从第 3 步起，恢复时绝不能用旧库覆盖。

## 6. 第 3 步：写入改走队列 + 推送线程（2026-10-21 完成）

### 6.1 开关

| 环境变量 | 默认 | 作用 |
| --- | --- | --- |
| `PORTAL_WRITE_MODE` | `cache` | `cache`（别名 `queue`）先进本地队列、立即返回；`direct` 直写飞书（回滚用） |
| `PORTAL_CACHE_TABLES` | `tasks,projects,schedule,procurement` | cache 模式下走队列的表；`members` 默认直写（考勤关键路径），可显式加回来 |
| `PORTAL_PUSH_ENABLED` | `1` | 推送线程开关（默认常开，direct 模式下也要排空遗留队列） |
| `PORTAL_PUSH_IDLE` | `5` | 队列空闲时多久查一次；有新写入会立即唤醒 |
| `PORTAL_PUSH_MAX_BACKOFF` | `300` | 临时失败的退避上限（秒） |

**默认不开启**。第 4 步起读接口已能立即看到本地改动，第 5 步（§8）补上了前端提示文案和
推送失败、冲突的页面展示与处理；生产上按表逐步切换见第 6 步。

### 6.2 组成

- **写入网关** `app/portal/writes.py`：所有写接口（事项、项目、日程、采购的增删改，组长批复）都走这里。
  - cache 模式：入队后立即返回，新建返回 `loc_` 临时 ID，响应带 `queued: true`。
  - direct 模式：仍直写飞书，写成功后顺手更新镜像。但这条记录如果还有排队中的操作，
    写入照样进队列，避免插到前面的操作之前。
- **推送线程** `app/portal/pusher.py`（线程名 `portal-push`），每条操作按下面的顺序处理：
  1. 读飞书上该记录的当前值；
  2. 按 §2 的规则算出要推的列，再写飞书；
  3. 写完重新读回，补上公式列，写回镜像；
  4. 推完请求一轮同步。
  - 失败时按类别处理：
    - 网络问题、限流、飞书临时性错误码（1254290/1254291/1254607/1255040）：退避重试；
    - 配置或权限错误：按退避上限慢慢重试；
    - 飞书明确拒绝：置为 `failed`，等人处理；
    - 程序异常：最多重试 5 次，之后置为 `failed`。
  - 服务启动时，上次中断、停在「推送中」的操作会重新排队。
- **两条额外规则**（补进 `cache_rules`）：
  - **日志类列直接覆盖**：成员表的「同步时间 / 同步说明」不做冲突判断，因为成员同步脚本每 5 分钟也会写这两列；
  - **推送时计算的指令**：以 `$` 开头的键在推送时按飞书当前值求值，不写进飞书。目前只有 `$rollover`（换周结算）。
- **考勤**（`members` 走队列时）：
  - 签到、签退先写本地考勤明细，飞书写入在**同一事务**里入队，所以签到状态立即生效；
  - 签退时长按增量推：飞书当前累计值加上本次时长；换周结算列用 `$rollover` 在推送时计算；
  - 零点作废和周一换周按本地视图判断，然后入队。镜像超过 15 分钟没刷新就不判断，等 10 分钟后重试；
  - 切到 cache 之前就已签到的会话，签退时会先接管进明细；跨零点的会复核一次飞书实时记录。
- **采购附件**仍直写飞书，因为要先上传文件。对象是临时 ID 时，最多等 15 秒让推送线程推完这条新建；
  前端新建采购后紧接着上传附件，靠的就是这个等待。上传完会写回镜像。
- **自动编号**会避开队列里还没推出去的编号。
- **飞书写客户端** `writer.py`：
  - 新建一律带 `client_token`，超时可以安全重试，direct 模式也受益；
  - 新增读单条记录 `get()`，记录不存在时返回 None；
  - 删除一条已经不存在的记录不再报错。

### 6.3 飞书接口实测（2026-10-21，正式库）

- 同一个 `client_token` 新建两次，返回同一条记录，表里只多 1 条。测试在空的值日表里做，测完已删除。
- 读单条记录不存在时返回错误码 `1254043`；读存在的记录带 `automatic_fields=true`，会返回 `last_modified_time`。
- 删除不存在的记录也返回 `1254043`；`batch_get` 会把不存在的 ID 放在 `absent_record_ids` 里。

### 6.4 观测与运维

- `GET /api/portal/sync-status` 多出 `cache` 字段，内容包括：
  - 写入模式、走队列的表、推送线程是否存活；
  - 待推、推送中、失败的条数，未确认冲突数，最老的未推送时间。
- 巡检 `scripts/portal_health.py` 新增退出码 **8**：有 `failed` 的操作，或最老的未推送改动超过 `--queue-age`（默认 900 秒）。
- 命令行 `scripts/portal_queue.py`：`status / list / retry / discard / conflicts / ack`，见运维手册 §8.2。

### 6.5 已知限制

- 读飞书和写飞书之间有毫秒级的窗口，这期间飞书侧的改动会被覆盖。不加锁，接受这个风险。
- 关联列（如事项的所属项目）不能指向还没推出去的临时 ID，接口按当前快照校验，会拒绝。
- 从 cache 切回 direct 前，先用 `portal_queue.py status` 确认队列为空。考勤的直写路径不经过队列，
  有积压时切回去，顺序无法保证。

## 7. 第 4 步：读接口看到本地改动（2026-10-21 完成）

### 7.1 做法

页面读的快照不再直接用飞书原始数据生成，而是用 **镜像 ⊕ 未落地操作** 经同一套规范化生成，
读接口本身一行没改。生成逻辑在 `app/portal/view.py`：

- **同步轮**：拉取飞书 → 保存列对照（飞书列名 → field_id）和记录链接 → 刷新镜像 →
  `view.rebuild(sync_round=True)`。用 `store.publish` 发布，带同步统计。
- **本地重建**：在下面这些时机触发，不访问飞书：
  - 网页写入后（cache 入队或 direct 直写写回镜像之后）；
  - 推送线程每推完一条后（包括冲突回退为飞书值、推送失败）；
  - 零点作废、换周入队之后。
  - 本地重建用 `store.publish_local` 发布，**不动** `last_success_at` 等同步统计，
    所以 stale 判定和巡检照样能发现同步故障。
- **其他规则**：
  - 内容哈希没变就不发布新版本，与原来相同；
  - 同步和本地重建共用一把构建锁，候选版本号的分配、写入和发布是串行的。
- **镜像刷新失败**：现在两种模式下都是整轮同步失败，保留上一版快照，
  因为快照来源就是镜像，镜像不可信就不能发布。

### 7.2 写形状在本地视图里的处理

排队中的操作是写入形状，规范化原本只认读取形状。这里有三处处理：

- **人员列**：排队中的值只有 open_id。重建时会从镜像里出现过的人员补上姓名，例如花名册、成员表等。
- **关联列**：排队中的值是 record_id 字符串数组。`normalize._link_id` 现在也接受这种形状。
- **附件**：上传后写回镜像时按读形状写，并带上文件名，否则规范化会把只有 token 的附件当成空。

### 7.3 临时 ID

- 本地新建还没推出去的记录，以 `loc_` 临时 ID 出现在列表和详情里。推出去后换成飞书 ID。
- 详情接口收到已经推出去的临时 ID 时，自动换成飞书 ID，所以停在详情页的用户不会遇到 404。
- 关联列可以指向临时 ID，比如新建事项时选择一个刚新建、还没推出去的项目。推送线程在推送前把它换成飞书 ID：
  - 对方还在队列里，2 秒后再试；
  - 对方的新建已经失败，这条置为失败。

### 7.4 direct 模式也受益

direct 直写成功后会写回镜像并本地重建，写完不用等下一轮同步就能看到。
签到、签退、跨零点作废的直写路径也补上了写回。

### 7.5 核对

- 2026-10-21 在正式库数据上比对：新流程「镜像 → 本地视图 → 规范化」生成的快照，和旧流程直接规范化
  飞书原始数据的结果**逐表逐条一致**（8 张表、41 条记录、质量问题都是 0），链接全部保留。
- 端到端测试（`test_portal_cache.py`）覆盖了这些情况：
  - 写完立即出现在列表里，飞书不可写时页面照样显示本地改动；
  - 冲突后页面回到飞书的值，临时 ID 的详情页推送后仍能打开；
  - direct 模式写完也立即可见。

### 7.6 没做的

- **只拉有变化的记录**（按 `modified_at` 增量拉取）：每轮整表拉取在当前规模下（几十条）不是瓶颈，暂不做。
- **飞书事件订阅**（长连接模式）：可以把飞书侧改动的延迟从 60 秒降到秒级，需要实测，暂不做。

## 8. 第 5 步：前端提示与同步状态（2026-10-21 完成）

### 8.1 写完立即刷新

- 写入接口返回时，后端已经把改动并进页面数据（第 4 步），所以 `store.afterWrite(res)` 只做两件事：
  显示提示、立即局部刷新。原来的「前端再请求一次同步 + 等 2.5 秒」去掉了
  （direct 模式由后端顺带请求同步，cache 模式由推送线程推完后请求）。
- 提示按响应的 `queued` 区分：排队的写「已保存，正在推送到飞书（通常几秒内完成）」，直写的写「已写入飞书」。
  后端 `_write_response` 的 `hint` 是同一套文案，前端优先用它。
- 删除成功后立即回列表（列表里已经没有这条），提示在列表页显示；签到 / 签退立即刷新状态。

### 8.2 记录上的同步标记

- 标记在**生成快照时**算好，存在记录的 `sync` 键里：`{"state", "label", "text"}`，
  没有标记的记录不带这个键。原料来自 `cache_store.record_marks`，文案在 `view.sync_mark`：
  - `failed` 同步失败：有操作被飞书拒绝（失败的改动不叠加到页面，页面显示飞书上的值）；
  - `conflict` 冲突：有未确认的冲突，点名冲突列；
  - `pending` 待同步：有未落地的操作，重试中会附上次失败原因。
  - 优先级：失败 > 冲突 > 待同步。
- 为什么放在快照里而不是读接口现算：标记一变快照内容就变，版本号随之更新，门户已有的轮询
  自然会刷新页面；各读接口也不用逐个查队列。
- 列表（事项、项目、日程、采购、总览、项目详情里的事项）显示小徽标，悬停看说明；
  详情页显示整句说明，手机上也看得到。前端组件 `web/src/portal/components/SyncMark.vue`。
- 新建推送失败的记录不会出现在列表里（失败的操作不叠加），只能在「数据质量」页看到。

### 8.3 推送队列与冲突的处理

- 接口：
  - `GET /api/portal/sync-queue`：失败、未落地的操作和未确认的冲突，整理成可读文字
    （`app/portal/queue_view.py`：记录名、改动的列、毫秒时间戳转日期、open_id 转姓名）；
    全员可看，`can_manage` 表示当前用户是否组长。
  - `POST /api/portal/sync-queue/{id}/retry`、`.../discard`、`POST /api/portal/conflicts/{id}/ack`：
    仅组长（`_require_leader`，含同源校验）；处理后立即本地重建，重试还会唤醒推送线程；记审计日志。
  - 重试 / 放弃一条**新建**时，同一记录上排在后面、被连带失败的操作一并处理（`cache_store.failed_after`）。
- 页面：「数据质量」页新增「网页改动推送」「冲突」两块；放弃用两步确认（`ConfirmButton.vue`）。
- 侧栏同步行带待推送 / 推送失败 / 冲突条数；有失败或冲突时圆点变色并给出「查看推送失败与冲突」入口。
  轮询除了比快照版本，也比较这三个计数，变了就刷新当前页。

### 8.4 没做的

- 命令行 `portal_queue.py` 处理后不触发本地重建（另一个进程，不能安全地抢发布版本号），
  页面上的标记要等下一轮同步才更新。
- 考勤页不显示成员行的同步标记（签到签退本来就立即生效，失败会出现在「数据质量」页）。
- 组长处理队列不按组别限制范围：任一组长都能处理任一条。
