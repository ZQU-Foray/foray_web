# 成员数据与原生考勤统计

## 数据入口

- 正式 Base：<https://<租户>.feishu.cn/base/<正式Base app_token>>
- 成员数据：`<members表ID>`，一行对应一个成员。保留用户建立的空行。
- 本表已接入门户只读同步（`config/feishu.json` 的 `members`，门户第 5 张同步表）：总览页「打卡工时排行」按`有效时长（小时）`降序展示，无考勤数据的成员列在末位并标「无数据」，空行不入榜。数字字段飞书返回为字符串，门户归一化时统一强转为数值。
- 工作事项：`<tasks表ID>`，组长维护事项与验收结果。
- 考勤明细（按日快照）已于 2026-09-12 随字段精简移除，程序不再维护该表。考勤只保留成员表的“最近签到 / 有效时长 / 异常考勤数”三项汇总；核对原始打卡请用飞书原生考勤后台。
- 当前仍采用管理员维护、成员只读；本次没有修改门户配置或切换测试 Base。

## 事项完成口径

成员归属只按事项“负责人”是否包含该成员判定；验收结论不是“取消”。赛季字段已随 2026-09-12 字段精简移除（本 Base 为单赛季工作库），不再按赛季过滤。多人负责的事项分别计入每个人，因此不能把个人数量相加当作战队总量。

| 字段 | 计算口径 |
| --- | --- |
| 有效事项数 | 全部未取消事项 |
| 已完成事项数 | 有效事项中验收结论为“通过”的数量 |
| 总体完成率 | 已完成事项数 ÷ 有效事项数 |
| 到期事项数 | 有效事项中有截止时间，且截止时间已到、位于统计起止范围内的数量 |
| 准时完成数 | 到期事项中已验收通过，并且提交验收时间不晚于计划截止的数量 |
| 准时完成率 | 准时完成数 ÷ 到期事项数 |
| 逾期未完成数 | 到期事项中尚未验收通过的数量，包含待验收 |
| 交付时间待补数 | 到期且验收通过，但未填写提交验收时间 |
| 未设截止事项数 | 有效事项中缺少计划截止的数量 |

两个比率分母为零时留空，不显示 0% 或 100%。准时完成率的分母包含逾期未完成事项，避免只看已完成事项造成虚高。例如 3 件到期事项中，1 件准时通过、1 件逾期通过、1 件未完成，准时完成率为 33.33%。

统计范围不再由表内字段指定（原“统计开始/统计截止”已随字段精简移除）：不传参数时不设界，即截至本次同步，与历史默认一致；需要限定区间时用 `--from-date`/`--to-date`，该区间同时作用于事项统计与考勤查询。截止时间填在未来仍只统计已经到期的事项；若按整月考核，止日传当月最后一天。“总体完成率”统计全部有效事项，不受统计区间过滤。

准时依据最终被验收认可的提交时间，而不是组长点击验收的时间，避免组长审核较晚影响成员准时性。退回后重新提交应更新提交验收时间；通过验收才算完成。样本少于 5 件时仅作参考。不把 P0—P3 作为效率权重：紧急程度与工作量不同，先分别看紧急事项和准时交付。

### 实现与刷新

之前的跨表日期计数公式未通过实测，现改用 `scripts/feishu_member_sync.py` 计算七项数量，再由表内公式计算两项比率和统计说明。“同步时间”与“同步说明”合并标明快照时效与本轮考勤结果。后台运行时默认五分钟一轮；停止程序后这些数量不会自动更新。

## 考勤口径

> 2026-09-17 起，「最近签到 / 最近签退 / 有效时长 / 异常考勤数」改由**门户打卡接口**（签到 / 签退）专有管理，`scripts/feishu_member_sync.py` 不再读取飞书原生考勤、也不再写这几列。本节以下为原生考勤时期的历史口径，仅供核对旧数据；当前的周结算见下一节。

程序使用应用身份获取成员 `user_id`，再调用飞书原生 `user_tasks/query`。默认统计上海时区本月 1 日至今天，每轮重新查询该范围，按七天分段，以覆盖补卡和管理员修正。可用命令行参数回填历史日期；当前成员汇总只展示最后一次运行指定的范围。

- 最近签到：统计范围内最近一条有效签到时间。
- 有效时长：同一成员有效签到与签退成对区间的并集时长。重复、重叠班段只计一次，支持跨午夜。
- 缺卡、待审批、无效、免打卡、系统生成的时间不补作真实打卡；不完整班段不计算时长。
- 异常考勤数：存在缺卡、时间不完整或原生迟到早退等异常的班段数；当前班段尚未签退也可能计入，不能直接当作违纪次数。
- API 失败：保留上次成功汇总及成功时间，更新失败状态。
- API 成功但无记录：清空该查询范围的时长与时间，明确提示核对考勤组和数据授权，不据此判定缺勤。

飞书打卡结果按班次返回，期间多次进出不一定完整呈现。有效时长是打卡覆盖区间，可能包含休息、外勤等，不能当作实际工作效率。程序不采集照片、定位、设备标识，不向飞书原生考勤写入记录。

## 周时长结算与值日表（2026-10-20 起，门户「02 考勤」页）

口径：一周 = 北京时间周一 00:00 至周日 24:00；本周时长**大于** 30 小时为达标（恰好 30 小时不算）。考勤页的数据全部来自飞书，组长可以在页面上给成员标「本周请假」（见下文「请假」）。逻辑集中在 `app/portal/attendance.py`，单元测试 `tests/test_attendance.py`。

### 成员数据表新增 7 列

| 列名 | 类型 | 谁写 | 含义 |
| --- | --- | --- | --- |
| 周初时长 | 数字 | 门户 | 本周开始时的「有效时长」累计值（换周时写入） |
| 结算周 | 文本 | 门户 | 周初时长属于哪一周：本周一的日期，如 `2026-10-19` |
| 上周时长 | 数字 | 门户 | 刚结束那一周的时长（换周时写入；结算周不连续时留空） |
| 本周时长 | 公式 | 飞书 | `有效时长 − 周初时长`（周初时长为空时等于有效时长） |
| 本周达标 | 公式 | 飞书 | `本周时长 > 30` → 达标 / 未达标 |
| 上周达标 | 公式 | 飞书 | `上周时长 > 30` → 达标 / 未达标（上周时长为空时留空） |
| 请假周 | 文本 | 门户 | 组长标了请假的那几周的周一日期，逗号分隔，如 `2026-10-12,2026-10-19`（2026-10-21 起） |

**请不要改这 7 列以及「有效时长（小时）」的列名**：门户写入时按列名写。

### 请假（2026-10-21 起）

- 组长在「考勤」页每位成员一行的「本周请假」按钮上点一下即可标记，再点「取消请假」撤销。只有组长看得到按钮，权限以服务端为准；操作记审计日志 `attendance_leave`。
- 标了请假的那一周：没达标（含待结算）时「达标」一栏显示「请假」，当天没签到时「今日」一栏也显示「请假」；达标了照常显示达标。顶部「本周已达标」的分母不算请假且没达标的人，并注明请假人数。
- 下一周自动恢复正常，不需要清理；上周请假且没达标的人，「上周」一栏显示「请假」。
- 门户写「请假周」时只保留本周与上周，更早的顺手清掉。也可以直接在飞书里改这一列，格式是周一的日期。
- 飞书里的「本周达标 / 上周达标」公式不变，仍只按时长判定；「请假」只是门户上的显示。

### 换周机制

- 每周一 00:00，门户的零点任务把每位成员的「周初时长」改成当时的有效时长，「上周时长」记下刚结束那周的时长，「结算周」改成本周一。之后签退累加有效时长，飞书公式随之算出本周时长。
- 「结算周」已是本周的行不会重复写，所以任何时刻重复执行都安全。服务在周一零点不在线时，启动后会补跑。签退时若发现本人还没换周，会在同一次写入里先换周，起点取签退前的累计时长。
- 签到跨零点会按既有规则作废，所以一次会话不会跨周。
- 页面只在「结算周 = 本周」时展示本周时长。换周还没同步到快照（通常 1 分钟内）的行显示「待结算」，不会把跨周累计的公式结果当成本周时长。一次都没签退过的成员本周按 0 小时显示。

### 值日表（新建数据表「值日表」）

| 列名 | 类型 | 说明 |
| --- | --- | --- |
| 值日安排 | 文本（主字段） | 可选备注，如「第 8 周」 |
| 日期 | 日期 | 按具体日期安排时填（调班、节假日） |
| 星期 | 单选：周一 … 周日 | 按星期轮换时填，每周重复 |
| 值日人员 | 人员（可多选） | 当天值日的成员 |

- 每行填「日期」或「星期」之一，再填值日人员。日期和星期都填了的行按日期算。
- 日常轮值按星期写 5–7 行，每周循环；临时调班或节假日另加一行写具体日期。某天只要有按日期的行，就只看日期行，同一星期几的轮换行当天不生效；同一天的多行日期安排会合并显示。
- 值日人员尽量用 @ 从通讯录选：这样按人员匹配成员数据表，考勤页成员列表里会标「值日」。
- 过期的日期行留着不影响，可以定期清理。门户每分钟同步一次，填好后 1 分钟内考勤页「今日值日」即更新。
- 从表格导入时，「值日人员」如果成了文本列，门户按姓名匹配成员（多个姓名用「、」或逗号分隔）；值日表里的人不在成员数据表中时，页面标「不在成员表」。
- 有内容但缺日期和星期、星期写法认不出、或没填值日人员的行，会出现在门户「数据质量」页。星期认得「周一 / 星期一 / 礼拜一 / 1 / Mon」等写法，周日也认「周天 / 星期天 / 7」。

### 开通步骤（需联网，在服务器上执行一次）

```bash
cd /opt/portal
export FEISHU_APP_ID=... FEISHU_APP_SECRET=...      # 或 source 运维用的环境文件
.venv/bin/python scripts/feishu_attendance_setup.py --dry-run        # 先看计划
.venv/bin/python scripts/feishu_attendance_setup.py --write-config   # 建列 / 建表 / 首次换周，并回填 config/feishu.json
```

- 2026-10-21 新增「请假周」列后需要再执行一次 `--write-config`：已有的列和表都会跳过，只补这一列并回填映射。
  没回填之前，考勤页不显示请假按钮，接口返回 503 提示先建列。

- 脚本是幂等的，可以重复执行：已有的列和表跳过；列类型不符只报告、不改。
- 首次换周会把本周起点设为执行时刻的累计时长。本周时长从这一刻开始累计，之前的累计时长无法拆分到周，不计入本周。
- `--write-config` 会先备份原配置为 `config/feishu.json.bak-attendance`。门户每轮同步都会重新读配置，所以不用重启；回填后 1 分钟内「考勤」页即显示周时长和值日。
- 值日表建好后，在飞书里把值日安排导入或填进这张表即可。也可以先导入一张名为「值日表」的表，再执行脚本，脚本会只补齐缺的列。
- 未开通前，考勤页照常显示累计工时排行，周时长与值日两块提示「未接入」。

需要应用身份权限 `attendance:task:readonly`、`contact:user.employee_id:readonly`，以及已经配置的读取成员、读写本 Base 的权限。开通后发布应用。考勤后台的数据授权范围应包含目标成员，并为成员建立合适的考勤组和班次。

2026-09-12 复验：五位成员的 `user_id` 与考勤接口均可调用（code 0），9 月 1 日至 12 日无返回记录，且 `invalid_user_ids`、`unauthorized_user_ids` 均为空——说明**数据授权范围已覆盖成员，缺的是打卡数据本身，不是权限问题**。下一步需确认考勤组与班次的分配，或等成员实际打卡后再核对时间值。程序会在下一轮查询中读取新增记录。

## 运行

Python 3.9+，标准库即可，Linux/WSL 环境。密钥不写入代码和文档；环境变量名称与已有门户一致。

```bash
python3 scripts/feishu_member_sync.py --prompt-secret
python3 scripts/feishu_member_sync.py --watch --interval 300 --prompt-secret
python3 scripts/feishu_member_sync.py --from-date 2026-09-01 --to-date 2026-09-12 --prompt-secret
```

首次部署、缺少同步字段时先运行 `--setup --prompt-secret`。`--setup` 只初始化本程序管理的统计与同步字段（七项计数、同步时间、同步说明），不恢复用户删除的业务表。程序通过文件锁阻止同一目录重复运行。

服务器常驻模板为 `deploy/feishu-member-sync.service`，默认部署目录 `/opt/portal`，复用该目录已有 `.env` 中的 `FEISHU_APP_ID` 与 `FEISHU_APP_SECRET`。安装前确认路径、正式 Base 与凭据匹配，先停掉手动启动的同步进程，再安装服务：

```bash
sudo cp deploy/feishu-member-sync.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now feishu-member-sync
sudo journalctl -u feishu-member-sync -n 30 --no-pager
```

服务模板已提供，未自动安装到生产服务器。前台 `--watch` 随终端进程/WSL 停止而停止，不能视作开机启动配置。结果文件 `docs/feishu-member-sync-result.json` 仅记录脱敏状态；空结果标记 `empty`，不是已有真实考勤数据。
