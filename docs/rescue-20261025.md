> 起因：2026-10-21 做完七次部署之后，开发机上的最新源码丢失。手里只有
> 2026-10-19 的「接续开发包（修复版）」和生产服务器上正在运行的服务。
> 本文记录从哪里恢复了什么、哪些是重建的、哪些确认丢失，以及验证证据，供以后排查时对照。

## 1. 结论

- **线上正在运行的代码已完整恢复**：服务器 `/opt/portal` 就是线上代码，后端 Python、前端
  `web/` 源码、测试、文档、systemd 单元全部取回。
- **前端源码与线上产物逐字节对应**：用取回的 `web/` 源码重新构建，`static/app/` 下 3 个入口
  HTML 与 10 个资源文件与线上**逐字节一致**，证明 `web/src` 就是线上前端的确切源码。
- **部署包里本来就不带的文件**做了重建（`deploy.py`、`web/package-lock.json`）或从 10-19 包补回
  （设计预览、参考素材、本地开发配置）。
- **确认丢失**：开发机上 10-21 最后一次部署之后若还有没部署的改动，无从恢复；另有少量本地
  产物（见 §4）。

## 3. 重建的部分

### 3.1 去掉的服务器残留

部署是“覆盖解压”，服务器上会累积已不属于代码的文件。整理入库时去掉了：

- `static/app/assets/` 里 21 个历次构建留下的旧哈希文件（入口 HTML 只引用当前一套 10 个）；
- `.zcode/`（2026-09 的 AI 工具规划稿）；
- `打包清单.md`、`文件清单.txt`（描述的是 10-19 的 zip 包，已过时；原件仍在 zip 里）。

### 3.2 `web/package-lock.json`

部署包不带锁文件，开发机上的原件随机器丢失。线上产物里的 Vue 是 3.5.39，而 npm 上 3.5.44 早在
10-13 就发布了，说明当时是从本地缓存离线安装的，不能简单装“当时最新版”。做法：按
`npm install --before=<日期>` 逐个尝试 vite/rolldown 版本组合，构建后与线上产物比对，最终确认：

| 包 | 版本 |
| --- | --- |
| vue | 3.5.39 |
| vite | 8.3.0（其依赖范围 `~1.2.6` 允许下面的 rolldown） |
| rolldown | **1.2.6**（决定压缩输出；1.2.4、1.2.8、1.2.14 等都对不上） |
| @vitejs/plugin-vue | 6.0.10 |
| typescript / vue-tsc / esbuild | 5.9.3 / 3.3.13 / 0.28.2 |

`package.json` 保持原样；`npm ci && npm run build` 后 13 个产物文件与线上逐字节一致。

### 3.3 `deploy.py`

部署包按设计不含 `deploy.py`，开发机上的 10-21 版本丢失。以 10-19 包里的旧版为骨架，按下列记录补齐
新行为：`接续开发说明.md` §4、`docs/portal-operations.md` §B.2 / §8.1、`docs/frontend-vue.md` §3、
`docs/portal-cache-design.md`、`tests/e2e/test_backup_restore.py` 对本模块的调用，以及服务器上留下的
产物格式（`code.tar.gz` 成员以 `./` 开头、不含 `.venv/config/firmware/.env`；`premigrate/` 由
`scripts/portal_migrate.py --backup-dir` 生成）。

| 行为 | 依据 |
| --- | --- |
| 凭据默认读 `config/deploy_server.json`，命令行与环境变量可覆盖 | 接续开发说明 §4 |
| 升级前备份 `config/`、`firmware/` 与旧代码 `code.tar.gz` | 同上；服务器备份目录结构 |
| 重启前跑快照库迁移，迁移前的库放 `<时间戳>/premigrate/`；迁移失败换回旧代码、不重启 | 运维手册 §B.2、§8.1 |
| 验证探针不过 → 自动退回旧代码、旧单元、迁移前快照库 | 接续开发说明 §4 |
| `--restore <时间戳>`（函数 `restore_previous`） | 同上 |
| `--rollback` 在旧调试台不存在时拒绝执行 | 同上 |
| 打包前校验三个前端入口与资源都在；排除 `node_modules/` | frontend-vue.md §3 |
| 排除设计预览；真实仓库打包 < 12 MB | test_backup_restore.py |

另外加了两处便利：`--list-backups` 列出可退回的时间戳；`--restore` 发现本地队列里还有没推到飞书的
改动时拒绝换回旧库（`--force` 才继续）。原版的具体实现细节（输出文案、步骤编号等）无法还原。

**验证**：`--dry-run` 通过（319 个文件、9.9 MB、零受保护路径、前端产物齐全）；
`tests/e2e/test_backup_restore.py` 31/31 通过（含对本模块的 6 项检查）；对生产服务器实测了只读路径——
读配置连接、sudo 预检、`--list-backups`、本地队列计数（0）、5 个线上探针（含新前端资源）全部正常。
**写操作路径（实际部署、退回）没有在生产上演练**，第一次用它部署时建议先在测试实例上走一遍，
或部署后立即用 `--list-backups` 确认备份已生成。

## 5. 验证结果（2026-10-25，本机 WSL Ubuntu 22.04，Python 3.10.12，依赖按 `requirements-lock.txt`）

- 前端构建：13/13 文件与线上逐字节一致。
- `vue-tsc` 类型检查：11 处既有错误（7 处 `aria-label` 与组件 `ariaLabel` 必填属性不符、3 处未使用变量、
  1 处 `aria-*` 类型），线上代码本来如此，构建不做类型检查所以不影响产物。为保持与线上一致，未修改。
- 单元测试（`python -m unittest tests.test_*`）：117 项，116 通过；`tests.test_feishu_member_sync` 的
  `test_attendance_failure_preserves_previous_snapshot` 失败——10-19 包里的同一份代码同样失败，属既有问题。
- 端到端回归（`tests/e2e/run_all.py`，18 个套件，Playwright 1.64 + Chromium headless shell）：
  **963 项检查，955 通过，8 失败**。逐项甄别：

  | 失败项 | 结论 |
  | --- | --- |
  | `test_acceptance` 6-8：探测 `192.168.1.130:8000` 的 5 项 | 环境：该预发实例已不存在（服务器已换地址）；本机设了 HTTP 代理时代理回 502 被记为失败，去掉代理后按不可达跳过 |
  | `test_acceptance`「失败记录错误类别 = network」 | 环境：本机 `http_proxy` 把“断网”请求变成了代理错误；去掉代理环境变量后通过 |
  | `test_acceptance`「负载下无 >1s 遥测断流」 | 本机两次实测最大间隔 2.8 s / 3.3 s（门槛 1 s）。可能是本机负载所致，**未在生产硬件上确认** |
  | `test_portal_cache`「临时 ID 的详情页推送后仍能打开」 | **时序问题**：测试只等队列清空，推送后本地快照换成飞书 ID 还要再晚几秒；在副本里加 3 秒等待后通过。线上影响：推送完成后几秒内用临时 ID 打开详情页会 404。代码与线上一致，未改 |

  跑回归时的两个环境坑：只补了库没放字体就建 `tests/e2e/browser-libs/` 会让 Chromium 崩溃
  （`SkFontMgr ... Not implemented`），改用 `LD_LIBRARY_PATH`；`test_tls.py` 需要仓库内的 Linux `.venv`。
